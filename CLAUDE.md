# Customers.Direct

AEO SaaS for local businesses and the agencies that manage them: checks whether ChatGPT, Claude and Perplexity recommend a business for local customer questions, shows why competitors win, gives fix steps, and tracks progress. Stack: Next.js 16 App Router, React 19, TypeScript, Tailwind v4, shadcn/ui, Supabase (auth, Postgres, pg_cron), Stripe, hosted on Netlify (Vercel only if the Netlify test fails, D-41).

## Engineering rules (MVP_SPEC 18.1)

- New code follows the layout in MVP_SPEC 18: thin routes in `src/app`, logic in `src/modules/<feature>/` (`dal.ts`, `actions.ts`, `service.ts`, `schema.ts`, `prompts/`, tests next to code).
- Only a feature's `dal.ts` (marked `server-only`) reads the database or secrets.
- Every Server Action and route handler checks auth itself (`requireUser()` / `requireAdmin()`); never rely on `proxy.ts` or a page-level check. `proxy.ts` does quick redirects only.
- Server Actions for UI mutations; route handlers only for Stripe webhooks, the job worker and public endpoints.
- Validate every input with zod. Return only the fields the screen needs, never whole rows.
- Read env vars only through `src/lib/env.ts`. Use generated Supabase types (`src/types/database.types.ts`); never hand-write DB types.
- Auth trust decisions use `getUser()` or `getClaims()`, never `getSession()`.
- Every table has RLS. Schema changes only through new files in `supabase/migrations/`; never edit an applied migration; additive changes only until the MVP is live (D-43).
- Features do not import each other's internals. Components never import Supabase, Stripe or AI clients.
- Keep files under 250 lines (hard limit 400). Split old oversized files when you touch them.

## Money and credits (MVP_SPEC 4, 11)

- Credits change only through the SQL functions (`hold_credits`, `capture_credit`, `release_hold`, `grant_credits`, `expire_grants`, `admin_adjust_credits`). Never update balances from app code.
- Credits are granted only by Stripe webhooks or admin actions. Every ledger row and webhook handler is idempotent (unique source key).
- Failed checks are never charged; a started scan always finishes (limited overdraft).

## AI features (MVP_SPEC 5, 25)

- Prompts live in `src/modules/<feature>/prompts/` as versioned files; evals import the same files.
- Pin exact model IDs. Checks: `gpt-4.1-mini` via the OpenAI Responses API, `claude-haiku-4-5`, `sonar`, each with web search and the business location as `user_location`. Explanations: `claude-sonnet-5`.
- Changing a prompt or model means running its eval suite in `evals/` (MVP_SPEC 25) and reporting the result.
- Eval rules: code graders before AI graders; AI graders pass/fail only; a model never grades its own output; correct answers are labelled by people, never generated by the model under test; API errors counted separately.
- Score = mention rate over 30 days, never a "rank in AI" (D-63).

## Google Places (MVP_SPEC 26)

Store only `place_id`. Never save business names, addresses, ratings or reviews from Places; fetch them live and show Google attribution. Places only pre-fills forms that the user confirms.

## Design (docs/design/DESIGN.md)

Use the design tokens and shadcn/ui; no raw hex colours in components. Blue `#2563EB`, 4px corners, light mode only, Lucide icons, plain-language wording (MVP_SPEC 8.4). Design empty, loading and error states. Use the `frontend-design` skill for UI work.

## Before calling a task done (MVP_SPEC 21)

Run `npx tsc --noEmit`, `npx eslint src`, the tests, and `npm run build`, and report the actual output. For UI changes, check screenshots at 1440px and 390px. Reference the decision or roadmap ID (`D-xx`, `SEC-01`) in commit and PR titles.

## Branches and protection (D-45, D-82)

- `main` is the live site (Netlify auto-publishes). Never commit or push to it directly; work on the task branch named in the build plan (`task/B-xx-name`) and merge by pull request into `main` or the long-lived `mvp` branch as the task says.
- Git hooks scan every commit and push for malware and secrets; never use `--no-verify`. If a scan fails, stop and report it.
- Never open or run code from branches the scanner flags.

## Safety

- The database is shared with the live site (D-43): back up before migrations, and test with an `is_test` agency so no real AI credits or payments are spent (D-61).
- Stripe work uses sandbox keys only.
- Never commit secrets or customer data; `.env*` files stay local.
